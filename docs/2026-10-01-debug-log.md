## 2. 配置检查与 BSP 编写

### 2.1 UART

- 使用 USART5，TX 为 PB3，RX 为 PB4。
- 配置为 `115200 baud / 8 数据位 / 无校验 / 1 停止位`。
- DMA RX 使用通道 1，DMA TX 使用通道 2。
- 发送示例帧为 `55 AA 05 10 20 30 40 50`，正常情况下每 1000ms 发送一次。
- 接收使用 `HAL_UARTEx_ReceiveToIdle_DMA()`，缓冲区为 256 字节。
- 完成发送完成回调、接收事件回调、错误回调，以及对应 UART、DMA 中断入口。
- 接收回调记录最近一次接收长度并重新启动接收，当前尚未加入业务协议解析。

### 2.2 双 CAN

| 配置项 | CAN1 | CAN2 |
| --- | --- | --- |
| RX 引脚 | PB8，AF3 | PB0，AF3 |
| TX 引脚 | PB9，AF3 | PB1，AF3 |
| 模式 | 正常模式 | 正常模式 |
| 帧格式 | 经典 CAN，标准帧，8 字节 | 经典 CAN，标准帧，8 字节 |
| 示例 ID | `0x101` | `0x202` |
| 示例数据 | `55 AA Seq 01 02 03 04 05` | `55 AA Seq 01 02 03 04 05` |
| 常规首发周期 | 100ms | 100ms |

- FDCAN 时钟为 64MHz；名义位时序为分频 4、TSEG1=11、TSEG2=4、SJW=1。
- 波特率为 1Mbps，采样点为 75%，关闭 BRS。
- 配置标准数据帧接收过滤器，接收进入 FIFO0；拒绝扩展帧和远程帧。
- 在 `User/comm_bsp.c`、`User/comm_bsp.h` 中集中实现通信 BSP，并接入工程构建和主循环。
- 完成 FIFO0 接收回调、错误回调及两路 CAN 的共享中断处理。
- 每路独立维护发送状态和序号，仅在确认发送完成后推进序号。

### 2.3 GPIO 控制

- 主循环每 500ms 同时翻转 PB12、PB13，完整周期为 1s。
- 初始化时将 PA15、PD0 设置为高电平，并同步更新 `CanIsolation.ioc`，使 CubeMX 配置与当前代码一致。
- CTR1、CTR2 已完成初步验证；本记录不根据代码中的 GPIO 编号推测板级信号映射。

## 3. 遇到的问题与排查过程

### 3.1 CAN2 发送不成功

初期 CAN1 可以发送，CAN2 未看到正常发送信息。调试中出现发送请求挂起、FIFO 满、发送完成计数为 0、接收计数为 0 等现象。

采取的排查工作：

1. 核对 CubeMX 和实际初始化代码中的引脚、AF、时钟、位时序、过滤器及中断配置。
2. 阅读 TD301DCAN 手册，确认其为 3.3V 逻辑供电，3脚 TXD 接 MCU TX，4脚 RXD 接 MCU RX；模块没有 EN/STB 引脚。
3. 将两路 CAN 接到同一总线进行测试，明确 CANH 接 CANH、CANL 接 CANL，并检查终端条件。
4. 使用 ST-LINK 读取发送状态、接收计数、协议状态、错误计数、发送队列和 GPIO 输入状态。
5. 区分“HAL 接收入队请求”和“硬件实际发送成功”，避免将入队成功误认为总线上已经发出有效帧。

当时曾出现 PB0 寄存器读到低电平，而模块端及芯片引脚实测约 3.19V 的情况。两种结果不是同步采样，不能仅凭该现象判定线路持续为低或芯片损坏。

临时开启 PB0 内部弱上拉后，输入读数变高，CAN2 开始尝试发送，但随后出现 Bit0 错误和 Bus-Off。该测试后恢复了原 GPIO 配置。

### 3.2 芯片重焊后 CAN1 也异常

重焊 MCU 后，故障表现发生变化：

- CAN1 的 PB8（RX）采样为低电平，发送请求持续等待，超时重发增加。
- CAN2 的 PB0（RX）采样为高电平，但发送时反复出现 Bit0 错误、Bus-Off；发送错误计数曾达到 248。
- Bit0 错误说明发送显性位时接收反馈不符合预期，需要检查完整的 TX、收发器、总线和 RX 反馈路径。

分别进行内部回环测试后，两路均可收发，短时测试中每路记录了 20 次发送完成、21 帧接收。该结果确认了控制器内部和软件接收中断路径可以工作，但不代表外部引脚、收发器和总线已经正常。

后续两路 CAN 恢复实际发送，接入同一总线后的实测也确认了正常通信。本次记录未确定此前全部 CAN 异常的单一硬件根因，不将其直接归因于 LED9 虚焊。

### 3.3 LED9 引脚虚焊

- 后续应补充复焊情况、控制电平与点亮/熄灭复测结果。
- 目前记录不足以确认 LED9 已修复，也未建立该虚焊与 CAN 异常之间的因果关系。

## 4. 自动恢复与重发

- 增加 `g_can1_status`、`g_can2_status`，记录发送完成、入队失败、超时、重试、Bus-Off 恢复及错误计数。
- 常规发送请求等待超过 1000ms 后，申请取消该缓冲区，等待异步取消完成后再发送；重试保留原序号。
- Bus-Off 时由主循环进行停止/启动恢复，恢复尝试间隔为 1000ms。
- 清除 INIT 后等待硬件完成总线恢复，避免持续重启打断恢复过程。
- 回调中记录错误，恢复操作放在主循环中执行。
- 调试观察到超时和重试计数增长，也观察到 Bus-Off 恢复次数增长，验证了对应逻辑实际运行。

软件恢复用于处理通信异常，不能替代对焊接、供电和外部反馈路径的检查。

## 5. 延迟统计与转发测试

### 5.1 CAN1 发送到 CAN2 接收

- 使用 TIM2 作为 32 位自由运行计数器，频率为 1MHz，计时分辨率为 1us。
- 从 CAN1 调用发送入队前计时，到 CAN2 FIFO0 回调读取匹配帧前结束。
- 通过 ID、序号及完整 8 字节数据匹配，避免将其他帧或重复接收计入统计。
- 使用 `g_can1_to_can2_latency` 记录样本数、最新、最小、最大和平均延迟。
- 该指标包含入队、仲裁、传输和中断响应时间，不是单独的收发器传播延迟。

### 5.2 CAN2 首发、CAN1 接收处理、CAN2 再次发送

测试路径：`CAN2 首发 → 外部 CAN 总线 → CAN1 接收中断 → MCU 读取并校验 → CAN2 再次发送`。

- 两路 CAN 均为正常模式，测试不使用内部回环。
- 首发和再次发送使用相同 ID `0x202`、DLC 和数据，CAN1 收到首帧后立即触发再次发送，不等待 100ms 周期任务。
- 通过状态和内部发送标记区分首发、转发，第二次收到同一帧不会继续转发。
- 两次实际发送的间隔使用 CAN2 Tx Event FIFO 的硬件时间戳，统计帧起始 SOF 到下一帧 SOF 的时间差。
- 当前 1Mbps 配置下硬件时间戳分辨率为 1us；设置 50ms 测量期限，避免 16 位时间戳多次回绕造成误判。
- 转发请求独立跟踪发送缓冲区，处理队列满、入队失败、超时和异步取消。
- 当前转发数据取自首发缓存，已与实际接收的 8 字节逐一核对一致；属于专用接收触发重发测试，尚未实现通用透明转发或额外业务处理。

完成编译、下载和校验后，在板上读取到以下实测结果：

| 指标 | 结果 |
| --- | --- |
| 有效样本数 | 1525 组 |
| 两次实际发送平均间隔 | 160.78us，累计总时间除以样本数 |
| 最新发送间隔 | 164us |
| 最小 / 最大发送间隔 | 156 / 165us |
| 累计发送间隔 | 245187us |
| 最新接收处理到再次入队耗时 | 29us |
| 最新两次入队间隔 | 252us |
| 转发入队失败 / 超时 / 发送事件错误 | 0 / 0 / 0 |
| 两路发送错误计数 / Bus-Off | 均为 0 |

较早一次读取为 539 组，后续增长到 1525 组；CAN1 接收计数为 3050，与每组首发、再次发送各接收一次相符。

`g_can2_forward_interval.average_us` 按整数保存，因此实时监视显示 160；160.78us 来自累计值计算。29us 是最新一组基础接收、匹配及再次入队耗时，不是平均值，也不包含额外业务计算。两次入队间隔还包含首次 CAN2 发送前等待 CAN1 示例帧的时间，不能与 SOF 间隔混为一谈。
